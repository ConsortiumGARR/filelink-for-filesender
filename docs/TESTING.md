# Test plan

## Automated (before every build)

    sh test/check.sh

It runs static checks, signing tests (JS vs `filesender.py`), request retry tests, the
background simulation and, when Chrome is installed, the real WebCrypto tests. Every
line must end with `ALL PASS`.

## Manual, in Thunderbird

Setup:

1. `sh tools/build.sh`, then Debug Add-ons -> remove the previous version -> "Load
   Temporary Add-on" -> `dist/filelink-for-filesender-1.0.0.xpi`. The install prompt
   lists: access to all websites, notifications and message composition (used only to
   know whether a mail was sent or saved).
2. "Inspect" on the extension -> Console -> "Persist Logs".
3. Fixtures in `test/files/`. The big ones are generated by `sh test/make_fixtures.sh`,
   which also prints the sha256 to compare after download.

   | File | Expected |
   |---|---|
   | `ok-small.txt` | upload ok, one chunk |
   | `ok accents àèìòù ñ ç (v2) [draft] #1.txt` | upload ok, allowed name |
   | `ok-5MB-exact.bin` | upload ok, exactly one chunk (boundary) |
   | `ok-5MB-plus-1-byte.bin` | upload ok, two chunks, the last of 1 byte |
   | `ok-12MB.bin` | upload ok, three chunks |
   | `empty.txt` | error: empty file |
   | `bad name è à ñ 😀 ： ⧸ «&+%#=» ü.txt` | error: name not allowed |
   | `blocked.exe` | error: extension not allowed |
   | `ok-199GiB.bin` | accepted: the upload starts (sparse, abort it) |
   | `too-large-200GiB.bin` | error: too large (sparse, never copy it) |

   The expectations on names, extensions and sizes assume the instance rules of the
   FileSender defaults (e.g. `.exe` banned, 200 GiB maximum); check
   `/filesender-config.js.php` of your instance.
4. For server-side checks use the "My transfers" page of the FileSender site.

Each item: what to do -> what to expect. The log line to look for is in parentheses
(enable debug logs in the settings).

### A. Account settings

- A1. Open the account -> fields in this order: Base URL, Identifier, API key, Sender
  email, "Test connection"; then the sections Terms of use, Behaviour, FileSender
  default upload options. The expiry list goes up to the instance maximum, with "Maximum
  allowed by this instance: N days".
- A2. Save without ticking the terms -> error, nothing saved.
- A3. Base URL `https://example.org` -> "Cannot read the configuration of the instance",
  expiry list up to 30 days. Put the right URL back.
- A4. "Test connection" -> "Connection OK" below the button (`credentials ok for ...`).
  On a new account the default options become those of your last transfer; on a saved
  account nothing changes. Terms and sender email are never touched. Save -> the yellow
  warning disappears; reopen -> values kept.
- A5. New account: the terms checkbox stays empty even after "Test connection"; without
  ticking it by hand the save is refused.
- A6. Wrong API key (or identifier), "Test connection" -> "FileSender rejected the
  credentials". Unreachable URL -> "Cannot reach FileSender". Restore the right values
  and save.
- A7. Empty sender email -> upload ok, sender = account primary email (`from (account
  default)`). An email not belonging to the account -> "The sender email is not one of
  the emails of your FileSender account".

### B. Direct upload, without the options window

In the account settings turn off "Ask for the upload options ... at every upload" and
save.

- B1. `ok-small.txt` -> no window; link in the mail with the default expiry; the
  transfer on the site has the default options (`upload start days N options {...}`).
- B2. `ok-5MB-exact.bin`, `ok-5MB-plus-1-byte.bin`, `ok-12MB.bin` -> links ok; once
  downloaded, sha256 equal to those printed by `make_fixtures.sh`.
- B3. `empty.txt` -> "The file is empty".
- B4. `too-large-200GiB.bin` -> Thunderbird's size limit message (or ours, "exceeds the
  maximum size"); no upload.
- B5. `ok-199GiB.bin` -> no size error, the upload starts; abort it at once (it would
  really send 199 GiB).
- B6. The bad-name file -> "The file name contains characters not allowed", immediately
  and without any window (`file name not allowed by the instance name`).
- B7. `blocked.exe` -> "The file extension exe is not allowed".

### C. Options window

Turn "Ask for the upload options" back on and save. From now on every upload opens the
"Upload with FileSender" window.

- C1. One file -> window with the file, expiry and default options.
- C2. Expiry 3 days, untick "Notify me on download" -> Upload -> mail with a 3-day
  expiry; on the site the option is off.
- C3. Pick 3 files at once -> ONE window with 3 files -> Upload -> 3 links (`options
  chosen for 3 file(s)`).
- C4. Cancel -> no upload, attachments aborted (`options cancelled`).
- C5. Close the window with the X -> as C4 (`options window closed, cancelling`).
- C6. With the window open on 2 files, abort one from the attachment pane -> it
  disappears from the window, the other uploads normally.
- C7. Tick "Recipients must log in to FileSender" -> if the instance does not allow it,
  notification "FileSender did not apply some options"; otherwise the download requires
  a login.

### D. Encryption

Encryption is enabled in the options window: "Encryption" section -> tick "Encrypt the
files with a password" -> the password field and the Show, Generate, Copy buttons
appear.

- D1. Tick it and type `abc` -> "Missing: ..." and Upload disabled.
- D2. Generate -> compliant password; Copy -> paste it somewhere.
- D3. Upload -> the mail says "password protected" (`upload start ... encrypted true`).
- D4. Open the link in a private window -> the page asks for the password -> download ->
  `sha256sum` identical to the original.
- D5. Wrong password on download -> FileSender error.
- D6. As D3-D4 with `ok-5MB-exact.bin`, `ok-5MB-plus-1-byte.bin` and `ok-12MB.bin`:
  identical sha256. This is the most important encryption test (chunk boundaries).

### E. Reuse from the attach menu (Attach -> Filelink -> file name)

- E1. File already uploaded and valid -> same link, no upload (`previous link transfer
  N`, `reusing link`).
- E2. Close that transfer on the site, then pick the file again:
  - options window on: options window with the reason in yellow "is no longer valid";
  - options window off: notification + new upload.
- E3. Upload with a 1-day expiry, then pick it again at once (expires within 24h) ->
  window "Reuse the FileSender link?" with the expiry date:
  - "Upload again" -> new upload (through the options window when on);
  - "Reuse the link" -> same link;
  - "Cancel" or X -> attachment aborted.
- E4. Reuse an encrypted upload (valid for more than 24h) -> window "Reuse the
  FileSender link?" with "valid until ..." and the password reminder; "Reuse the link"
  -> the mail says "password protected"; "Upload again" -> new upload, also without
  encryption.
- E5. Attach the same file from disk (not from the menu) several times with the maximum
  expiry -> a new upload each time, never `bad_expire`; the expiry is N days later at
  the same time of day, as in the web UI. Only the attach menu reuses links: from disk
  Thunderbird does not pass the previous link.
- E6. Change the file on disk (e.g. `echo x >> file`) and pick it again from the menu ->
  reason "has changed", new upload.

### F. Abort and robustness

- F1. Big file, abort during the upload -> it stops at once (`upload aborted`); no
  transfer left on the site.
- F2. Long upload (a few minutes) with DevTools CLOSED -> it completes. Checks that the
  event page is not idle-terminated (keepalive).
- F3. Thunderbird in Italian and in English -> window, settings, errors and
  notifications follow Thunderbird's language.
- F4. Options window with encryption: typing the password does not change the window
  height (it changes only when lines appear or disappear, e.g. "Missing: ...").
- F5. Options and reuse windows -> centered on the compose window and still centered
  when their height changes. On Wayland the compositor decides the position (GNOME:
  `org.gnome.mutter center-new-windows`).
- F6. Same file uploaded several times: the attach menu shows one entry per name, bound
  to the first upload; "FileSender…" + browse always uploads again (even with the same
  password: new salt and IV).
- F7. Very long upload (e.g. `ok-199GiB.bin`): after a few minutes Thunderbird may show
  "Save Draft Error ... error attaching". It is the draft autosave, which cannot include
  a file still being uploaded. The upload goes on; it does not depend on the extension.

### G. Cleanup of transfers of unsent mails

With debug logs on, the console shows `deleting transfer of a mail not sent` or
`transfer kept (mail sent or saved)`. Always check the site as well.

- G1. Upload a file, close the mail without sending or saving -> the transfer disappears
  from the site.
- G2. Upload a file, remove the attachment from the mail -> transfer deleted.
- G3. Upload a file and send the mail -> the transfer stays.
- G4. Upload a file, save as draft, close -> the transfer stays (also when the autosave
  kicked in).
- G5. Upload a file in mail A; in mail B reuse it from the attach menu; close A without
  sending -> it stays (B uses it); close B without sending too -> deleted.
- G6. Reuse from the menu a link of a mail already sent, then close without sending ->
  the original transfer stays.
- G7. Remove the FileSender account from the settings -> its saved settings are deleted
  (adding it again shows an empty page).

### H. Icons and logs

- H1. The yellow FileSender icon appears in the add-ons list, in the Attach -> Filelink
  menu and in the FileLink box of the mail.
- H2. Debug off -> only errors in the console. Debug on -> every step; the API key, full
  tokens, full signatures or plain email addresses never appear.
